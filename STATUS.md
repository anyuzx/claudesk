# claudesk Project Status

**Last reviewed:** 2026-09-15
**Checkout when reviewed:** public source snapshot prepared from the private development baseline
**State:** Phase 2 core app is complete. Phase 3 work is active across PDF/full-text workflows, AI context, semantic search, workflow polish, desktop polish, and integrations.

## Product Snapshot
Claudesk is a single-user, local-first research workspace:

- FastAPI backend serving `/api/*` and the built React app.
- React/Vite frontend with tabs for Digest, Saved, Notes, Tasks, Reading Queue, Log, Projects, Search, and Settings, plus persistent side-panel Chat.
- SQLite database at `<vault>/claudesk.db`; default vault is `data/`, with per-machine vault pointers for Dropbox-style sync.
- Daily digest over arXiv, bioRxiv, PubMed, and OpenAlex.
- First-class markdown notes, task tracking, durable log entries, project coordination, managed paper PDFs, and persistent chat.

### Papers, Sources, And Ranking
- Source adapters are implemented for arXiv, bioRxiv direct API with Crossref fallback, PubMed auto/builder/raw strategies, and OpenAlex. PubMed generated auto/builder searches are length-aware: Settings preview reports encoded ESearch length and warnings, generated overlong searches are split with exclusions preserved, PMIDs are deduped and capped to `digest.max_per_source`, and request-too-long ESearch failures are normalized.
- Digest fetches, deduplicates by DOI/title, ranks with local embeddings, optionally applies OpenAI rubric scoring, and writes digest runs to SQLite.
- Digest runs and manual rubric-scoring runs create durable `background_jobs` records with progress events, failure rows, cancellation/reconciliation state, and the existing specialized API response shapes. Their child-process execution still uses the existing process-job adapter so embedding/model memory is released after each run.
- Paper state separates saved, read, to-read, and dismissed. Dismissed papers are hidden from default list/search surfaces and recoverable through explicit controls.
- DOI add/merge and duplicate repair preserve user state, notes, project links, feedback, linked ids, and `paper://` mentions.
- `seed_papers` is accepted by config but is not used by ranking yet.

### Notes, Tasks, Log, And Projects
- Notes are first-class markdown records linked to papers through `note_papers`, with mention-derived links from `paper://<id>`. Note-to-note links derive metadata into `note_links` and use id-backed Markdown such as `[@Target Note](note://104)` once a target exists, while legacy `[[Target Note]]` wikilinks remain readable for unresolved/create-note flows. Link states include resolved, unresolved, ambiguous, missing-heading, and missing-target; Preview renders compact note links with click-to-open and unresolved click-to-create behavior, Source mode and Live mode both offer note-link completion, and the note workspace rail exposes outgoing note links plus backlinks.
- Note bodies remain canonical Markdown strings. The default live editor is the Milkdown-on-ProseMirror WYSIWYG Markdown editor, with CodeMirror retained for source Markdown mode and shared Markdown rendering for preview mode. Rich live editing includes inline strikethrough, highlight, subscript, superscript syntax, equivalent `> [!type]` and fenced `ad-type` admonitions with type autocomplete, title-as-label rendering, and per-type icons, metadata-preserving fenced code blocks, Crepe-compatible Markdown figure images from typed syntax or the slash menu with centered rendering/captions/drag resizing, paper mention link insertion from the slash menu with paper autocomplete, inline slash insertions for links, inline math, footnotes with a prompt, task-list items, and paper links, top-level non-table block dragging through a Milkdown block handle, plus a rich-editor context menu with clipboard actions and image data copy/internal-link/delete actions. GFM task-list items can be completed or reopened by mouse click in Preview and Live modes while preserving canonical Markdown source, using consistent checkbox styling and muted checked-item text. PNG, JPEG, WebP, and GIF images pasted or dropped into notes are stored under `<vault>/assets/images` and inserted as portable `asset://<id>` Markdown image references in both source and rich-editor paths.
- Task descriptions, manual log entries, project descriptions, and project milestone description/acceptance-criteria fields use the same shared Milkdown WYSIWYG Markdown editor field while still storing canonical Markdown strings.
- Tasks are stored in `todos` and served through `/api/tasks`.
- Log entries are stored in `log_entries` and served through `/api/log`; project-specific log reads use `/api/projects/{project_id}/log`.
- Tasks support one subtask level. Completing a root task creates one deduped `task` log row in `log_entries`; task log title/body/subtasks/project links/paper links are derived from the current task tree.
- Shared paper lifecycle writes and task/manual-log workflows live in focused core service modules, with API routes, agent capabilities, and CLI commands acting as thin adapters around them.
- Projects link many-to-many to papers, tasks, manual log entries, and chat sessions through join tables. Task log project membership follows the backing task projects.
- Project milestones are first-class project progress records with kind/status/order/acceptance criteria, linked tasks through `project_milestone_todos`, a counts-only `/api/projects/{project_id}/progress-summary` endpoint, a frontend Project Workspace Progress tab, and controlled agent milestone context/write tools. Numeric progress scoring, milestone weights, project phase/current-summary fields, and evidence links remain deferred.

### Managed Assets And PDFs
- Durable paper and Markdown image assets live under `<vault>/assets` and are addressed by asset ids, not arbitrary local paths.
- Paper workspace ASSETS supports upload, list, rename, remove, parse/reparse, status display, and in-app PDF open.
- In-app PDF reading uses the official `pdfjs-dist` viewer layer for loading, range-backed rendering, page lifecycle, text layers, navigation, zoom/fit-width, in-viewer search, outline navigation, and lazy thumbnails.
- PDF parsing stores normalized document blocks, page records, parser artifacts, derived chunks, FTS rows, and rendered page images.
- PDF parse/reparse requests create asset-scoped durable `pdf_parse` background jobs keyed by asset id while preserving the existing immediate API response and `assets.parse_status` UI contract. Same-machine stale parse jobs reconcile on startup so assets do not remain `queued` indefinitely after a restart.
- Default parser is PyMuPDF. PyMuPDF4LLM, Docling, and MinerU are optional local backends.
- Chat-owned attachments for long pasted text, text-like files, images/screenshots, and PDFs use managed asset storage; chat PDFs reuse the same parser/cache path.

### Chat And Agent Runtime
- Chat sessions persist their own validated backend/model/runtime settings. Settings defines defaults copied on creation; backend switches reset to the target backend's defaults. Assistant instructions, tools, skills, native Codex permissions, and credentials remain global.
- Chat and Settings share a searchable model dropdown backed by `/api/chat/models`: OpenAI uses the configured account's Models API and Codex uses paginated app-server `model/list`. Gemini and Claude use built-in lists. Results cache for 15 minutes by provider identity, support explicit refresh, and retain same-identity results with a stale warning on discovery errors.
- Model choices carry compatible controls/defaults; unverified OpenAI families and models without image-input support are disabled. Saved unlisted IDs remain visible without becoming new selectable choices. Manual model-name entry and old model-override/global-footer mutation paths are removed.
- OpenAI chat uses Pydantic AI's Responses adapter with `store: false`; reasoning models omit unsupported sampling settings while retaining capability tools, image inputs, activity, and read-ledger handling.
- First-chat creation is shared by uploads, sends, and runtime saves. Failed model saves keep the confirmed selection and allow the same choice to be retried.
- Runtime updates are atomic and clear only the changed session's provider state. Active turns reject runtime updates and overlapping sends; Codex sessions with different models/options reuse the shared app-server process.
- Chat sessions and messages persist in SQLite. User turns can include visible context attachments for papers, projects, notes, PDF assets, and chat attachments.
- Assistant messages persist compact Activity trace entries for context, progress, tool calls/results, warnings, and errors. Raw provider reasoning is not stored or shown.
- `chat_resource_reads` records local resources supplied to API and Codex/MCP turns; the Activity panel can lazily show compact resource-read evidence.
- API providers run through Pydantic AI runtime adapters. Codex research chat runs through Codex app-server from `<vault>/codex-chat-workspace`.
- The Claudesk MCP server uses the official MCP Python SDK and exports tools from the canonical capability registry.
- Current capability registry count is 50 and includes `search_notes`, chat-attachment and local PDF tools, and project milestone tools.
- Agent write tools are intentionally limited to approved task/project/milestone/log/note/paper/PDF-asset actions. There are no completion, reopen, delete, project-status, or broad paper-status tools.
- API-provider and MCP tool runtimes convert capability/domain exceptions into tool error payloads and roll back pending transactions after failed capability execution.

### Settings And Frontend
- Settings uses schema-driven `GET/PATCH /api/settings`; deprecated `/api/settings/sources` and `/api/settings/digest` routes are gone. PubMed preview includes generated query text, empty status, encoded ESearch length, chunk count, and length warnings.
- Storage Settings shows the effective vault path, source, local config, settings file, database, and asset root, with target-path preview and confirmation before saving the machine-local pointer.
- Storage Settings also owns semantic search index status, update, and rebuild controls because the LanceDB index is local rebuildable storage close to managed paper PDFs.
- Most UI Settings patches clear `load_config()` for live-editable keys; manual YAML edits require restart.
- Tailwind CSS v4 is CSS-first. `frontend/src/index.css` owns theme tokens, font utility aliases, typography plugin import, light/dark variables, and Markdown prose overrides.
- Shared Base UI-backed primitives live under `frontend/src/components/ui/`; feature code should use local wrappers before adding UI surface.
- Project-link controls share one Base UI dialog/combobox flow across paper, task, log, and chat surfaces.
- Projects pane uses a toolbar, summary stripe, and metrics-backed table with status/progress/updated columns, plus context-menu status changes, chat-context attachment, and confirmed delete.
- Project workspace has scoped inline saves for title/status/description, a redesigned Overview tab with derived state, narrative, activity, and material summaries, a Progress tab backed by project milestones, a Tasks tab backed by the project-scoped task table, and a Log tab backed by project log reads.
- Note workspace has a native sticky right contents/snapshot rail derived from the current markdown draft, with the note body centered independently, paper-workspace-aligned note title/body typography, math-rendered heading labels, preview heading navigation, edit-mode editor jumps, shared Preview/Live collapsible heading state, and block-equation snapshot counts.
- Preview mode keeps small notes on the full shared `MarkdownContent` path and virtualizes large chunked previews with TanStack Virtual, using chunk height estimates, dynamic measurement, and outline-target range forcing while keeping Source and Live editor paths separate.
- Tasks pane is task-only. Task table filter/sort state persists in browser-local `tasksPaneTablePrefs`; root subtasks are collapsed into expandable parent rows with nested subtask menus.
- Reading Queue is a first-class sidebar pane backed by `/api/papers/to-read`.
- Normal Search defaults to fast local text search with a compact result-type combobox that supports multi-select filtering and no user-facing Keyword/Meaning/Best mode name. Embedding-powered expansion is an explicit per-surface opt-in in Search, Digest, Notes, Projects, Tasks, and Log through an icon-sized semantic toggle embedded in each search field; helper copy is omitted and semantic index readiness is shown as status-only after that surface enables embeddings. PDF chunk results render bounded snippets with stable paper/asset/page/chunk/block/bbox locators and open the in-app PDF viewer at the matching evidence when paper and asset ids are present.
- Pane-local search in Digest, Notes, Tasks, Log, and Projects follows a search-result-mode contract: while a query is active, browse filters, sorts, grouping, and status/date/project controls stay visible but paused, and retrieval results are not silently hidden or reordered by those browse controls. Each pane stores its embedding enhancement preference independently. Dismissed papers remain hidden outside global Search unless an explicit include-dismissed control is present.
- The app shell is desktop-first with shadcn Base sidebar foundations and Electron macOS/Linux titlebar handling.

## Database Snapshot
- `SCHEMA_VERSION = 42` is exported from `claudesk/core/db/__init__.py` and defined in `claudesk/core/db/connection.py`.
- `claudesk/core/db/` is split into focused infrastructure, schema/migration, paper, note, project, task/log, asset/PDF-cache, chat, and utility modules. The package entrypoint exports only `SCHEMA_VERSION`, `db_path`, `get_connection`, and `init_db`.
- Main tables include `papers`, `digest_runs`, `background_jobs`, `background_job_events`, `background_job_failures`, `notes`, `note_papers`, `note_assets`, `note_links`, `projects`, `project_milestones`, `project_milestone_todos`, `todos`, `log_entries`, `feedback`, `chat_sessions`, `chat_messages`, `chat_resource_reads`, `chat_attachments`, `assets`, `paper_assets`, `asset_pdf_pages`, `asset_parse_artifacts`, `asset_document_blocks`, `asset_text_chunks`, project join tables, and FTS virtual tables.
- Project join tables include `project_papers`, `project_todos`, `project_milestone_todos`, `project_log_entries`, and `project_chat_sessions`.
- Search tables are `papers_fts`, `notes_fts`, `todos_fts`, `projects_fts`, `log_entries_fts`, and `asset_text_chunks_fts`.
- Search orchestration enters through `claudesk/core/retrieval/`, which wraps SQLite FTS5 paper, note, project, task, log, and PDF chunk paths plus optional LanceDB semantic search with typed query, scope, snippet, score metadata, result hit, source type, and evidence-locator models. Lexical remains the default backend and never imports the embedding stack; `hybrid` adds semantic embeddings to fast text results; `semantic` remains an explicit compatibility/advanced backend.
- Core retrieval enforces source and project scopes directly. It supports global search, paper-only, notes-only, PDFs-only, paper-linked note search, project-scoped paper/note/task/log/PDF chunk search, and paper/asset-constrained PDF chunk retrieval through the retrieval request scope.
- The retrieval package has a LanceDB-backed semantic index service for rebuildable paper, note, project, task, log-entry, and parsed PDF chunk rows. It stores derived index data under the machine-local retrieval-index cache outside the synced vault, uses local `all-MiniLM-L6-v2` normalized 384-dimensional embeddings, records embedding model name/dimension/version plus content hashes, and supports full rebuild plus an incremental-update entrypoint that currently falls back to full rebuild for stale/deleted-row correctness.
- Fast text search preserves exact FTS5/BM25 matches first, then uses safe prefix matching for incomplete terms, relaxed multi-term fallback, and RapidFuzz typo-tolerant reranking over bounded FTS candidate pools only. Snippets remain grounded in concrete matched source text. `/api/search` preserves the existing response shape and defaults to lexical all-search while accepting additive `backend=lexical|semantic|hybrid` and one or more `type=all|papers|notes|projects|tasks|log|pdfs` query parameters. Semantic-only hits must pass conservative absolute/relative relevance thresholds before returning; hybrid keeps lexical hits and admits semantic-only hits only after that gating. PDF search responses include narrow paper/asset/chunk/page/section/block/bbox locators and bounded snippets only when PDFs are requested. `/api/search/semantic-index/status`, `/rebuild`, and `/update` expose sanitized index readiness and explicit maintenance actions without exposing LanceDB internals; the frontend places those actions in Settings > Storage. Agent paper search, note search, `retrieve_paper_context`, and `search_paper_pdf` accept the same backend modes; semantic hits are hydrated from live SQLite rows before returning payloads, and PDF semantic evidence verifies the live paper/asset/chunk relationship.
- Legacy names such as `progress_log`, `project_progress_entries`, `progress_fts`, and `completion_log_entry_id` are migration-only; new code should use `log_entries`, `project_log_entries`, and task-backed log rows.
- SQLite stays in DELETE journal mode for Dropbox compatibility.

## Known Gaps
- `seed_papers` and several ranking/paper-behavior settings are persisted but not fully consumed.
- Feedback rows are stored but not used for personalization.
- Semantic search and index maintenance are explicit user-triggered actions; there is no automatic background rebuild scheduler.
- The semantic-index incremental update entrypoint currently uses the full rebuild fallback for correctness across stale and deleted rows.
- OCR/scanned-PDF handling, cropped figure/table extraction, PDF annotations, and a general PDF discovery/download interface remain follow-ups. The agent can already attach a PDF from an HTTPS URL.
- `obsidian_note_path` exists on projects but no rich Obsidian project bridge is implemented.
- Zotero/Paperpile integration, note export to Obsidian, and broader document ingestion are not implemented.
- Chat session metadata links exist but richer search/pinning/session workflows remain open.
- Rich live Markdown editing is now the default note path and is shared by task/log/project body fields, with CodeMirror kept for note source Markdown mode. Large-note performance and remaining Markdown round-trip edge cases still need focused hardening in the rich editor path.
- Automated and Playwright coverage is focused, not comprehensive.
- No dependency-backed Python linter/typechecker or frontend lint config is configured.
- Dropbox two-machine sync is supported at the storage-model level, but concurrent writes from two running app instances remain untested.
- Semantic-index rebuild/update still uses its existing thread/global job state; porting it to `background_jobs` remains a later slice and is out of scope for the PDF parse follow-up.
